# 7.5 Log-Formatierung (KI-Readiness & Strukturierung)

## Konzept: Warum strukturierte Daten?

Roh-Logs (Plain Text) sind für Menschen gut lesbar, für Maschinen aber schwer zu interpretieren. Um eine KI-gestützte Sicherheitsanalyse (Phase 8) durchzuführen, müssen wir die Daten „normalisieren“.

- **JSON (Windows):** Ideal für komplexe Events mit vielen Unterfeldern. LLMs wie LLaMA3 verstehen die JSON-Syntax nativ und können Relationen zwischen IDs und Usern herstellen.
- **CSV (Netzwerk):** Ideal für Firewall-Ereignisse. Durch die Trennung mit Semikolons kann die KI statistische Auswertungen (z. B. „Top 10 Blocked IPs“) effizienter durchführen.

## Schritt 1: Windows-Events in JSON transformieren (DC-01)

Da Windows-Events binär vorliegen, nutzen wir auf dem `SRV-DC-01` ein PowerShell-Skript, das die im Staging gesammelten Events konvertiert und auf den Kali-Hub (`10.0.30.20`) schiebt.

**PowerShell: EVTX to JSON Push**

```powershell
# Ziel: Samba-Share auf der Kali-VM (Modul 7.4)
$Destination = "\\10.0.30.20\LogDropzone"
$FileName = "WinEvents_$(Get-Date -Format 'yyyyMMdd_HHmm').json"

# Die letzten 500 Sicherheitsereignisse strukturiert extrahieren
$Events = Get-WinEvent -LogName "ForwardedEvents" -MaxEvents 500 -ErrorAction SilentlyContinue
$StructuredData = $Events | ForEach-Object {
    [PSCustomObject]@{
        Timestamp = $_.TimeCreated; ID = $_.Id; Level = $_.LevelDisplayName;
        User = $_.UserId; Machine = $_.MachineName; Message = $_.Message
    }
} | ConvertTo-Json -Compress

# Als Datei zum Kali-Hub pushen
$StructuredData | Out-File -FilePath "$Destination\$FileName" -Encoding utf8
```

*Als Datei:* [`scripts/07-log-aggregation/7.5-powershell-evtx-to-json-push.ps1`](../../scripts/07-log-aggregation/7.5-powershell-evtx-to-json-push.ps1)

## Schritt 2: rsyslog Normalisierung auf Kali (CSV-Format)

Wir bringen der Kali-VM bei, ankommende Syslog-Pakete (von OPNsense und Linux) direkt in einem strukturierten CSV-Format zu speichern.

**2.1** Öffnen Sie die Konfiguration auf dem Kali-Client: `sudo nano /etc/rsyslog.conf`

**2.2** Definieren Sie ein neues Ausgabe-Template **vor** den Log-Regeln:

**rsyslog Template Definition**

```bash
$template AI_Struktur,"%TIMESTAMP%;%HOSTNAME%;%syslogtag%;%msg%\n"
```

**2.1** Passen Sie die Speicherregel für Netzwerk-Logs an:

```bash
# Nutzt das Template fuer alle Netzwerk-Logs
*.* /var/lib/siem-hub/syslog/network_structured.csv;AI_Struktur
```

**2.1** Starten Sie den Dienst neu: `sudo systemctl restart rsyslog`

## Schritt 3: Automatisierung via Task Scheduler (DC-01)

Damit die JSON-Dateien kontinuierlich auf dem Kali-Hub eintreffen, richten wir eine geplante Aufgabe ein.

- **Trigger:** Alle 15 Minuten.
- **Aktion:** `powershell.exe -ExecutionPolicy Bypass -File C:\Scripts\ExportToKali.ps1`
- **Benutzer:** `ad\svc-log-push` (Der Service-Account aus Modul 7.4).

## Verifizierung der Datenqualität

Prüfen Sie auf dem Kali-Client im Verzeichnis `/var/lib/siem-hub/`:

a.) **JSON Check:** Öffnen Sie eine Datei in `windows-json`. Sieht die Struktur korrekt aus? (`{"Timestamp":` `... }`)

b.) **CSV Check:** Führen Sie `tail /var/lib/siem-hub/syslog/network_structured.csv` aus.

> [!NOTE]
> **Portfolio-Check: KI-Optimierung**\
> Dokumentieren Sie, dass Token-basierte KIs wie Ollama bei strukturierten Formaten weniger Rechenleistung für das Parsen verschwenden und somit mehr Kontext für die eigentliche Bedrohungserkennung (*Threat Detection*) nutzen können. Sie haben hier eine Pipeline geschaffen, die Rohdaten in Wissen verwandelt.
