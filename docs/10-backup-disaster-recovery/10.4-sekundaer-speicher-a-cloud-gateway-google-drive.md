# 10.4 Sekundär-Speicher (A:) & Cloud-Gateway (Google Drive)

## Konzept: Tiered Backup Storage & Die 3-2-1 Regel

Um Kosten und Speicherplatz optimal zu nutzen, unterteilen wir unsere Backup-Architektur in verschiedene Zonen (Tiers) und erfüllen im gleichen Zuge die goldene **3-2-1 Backup-Regel** (3 Kopien, 2 Medien, 1 Offsite-Standort).

- **Tier 1 (Laufwerk B:):** Das 3x8TB RAID 5 (Volume 1). Hochverfügbar und durch NVMe beschleunigt. Hier liegen die primären Backups der DCs und Firewalls (Modul 10.2).
- **Tier 2 (Laufwerk A:):** Die 1x14TB HDD (Volume 2). Keine Ausfalltoleranz (JBOD), aber enormer Platz. Ideal für unkritische Test-VMs, alte Archive oder als Zwischenspeicher.
- **Tier 3 (Cloud / Google Drive):** Unser Offsite-Standort zum Schutz vor Elementarschäden (Feuer, Diebstahl) oder Totalverschlüsselung des lokalen Labors.

## Schritt 1: Bereitstellung von Laufwerk A: (14 TB)

Analog zu Laufwerk B: binden wir den 14TB Speicherpool der UGreen NAS per iSCSI an.

**1.1 NAS-Konfiguration:** Öffnen Sie den *SAN Manager* in UGOS Pro. Erstellen Sie eine neue iSCSI-LUN auf **Volume 2** (dem 14TB Pool) und weisen Sie diese einem Target zu.

**1.2 Windows-Einbindung:** Öffnen Sie auf dem `SRV-BKP-01` den *iSCSI-Initiator* und verbinden Sie sich mit dem neuen Target.

**1.3 Formatierung:** Öffnen Sie die Datenträgerverwaltung (`diskmgmt.msc`). Initialisieren Sie das neue Laufwerk als GPT, weisen Sie den **Laufwerksbuchstaben A:** zu und formatieren Sie es zwingend mit **ReFS (64K Blockgröße)**.

## Schritt 2: Secondary Repository in Veeam anlegen

Teilen Sie Veeam mit, dass nun ein weiterer Speicherplatz zur Verfügung steht.

**2.1** Öffnen Sie die Veeam Console → **Backup Infrastructure** → **Backup Repositories**.

**2.2** Klicken Sie auf **Add Repository** → *Direct attached storage* → *Microsoft Windows*.

**2.3** Nennen Sie das Repository **`REPO-NAS-Secondary`**.

**2.4** Wählen Sie unter Pfad Ihr neues Laufwerk **`A:\`** aus.

**2.5** Belassen Sie die *Fast Clone* Option für ReFS aktiv und schließen Sie den Assistenten ab. Sie können nun weniger kritische VMs gezielt auf dieses Repository sichern lassen.

## Schritt 3: Rclone Installation (Das Cloud-Gateway)

Da Veeam in der kostenlosen Community Edition (und ohne teure S3-Gateways) nicht nativ auf Google Drive sichern kann, nutzen wir das Open-Source-Tool **rclone**. Es agiert als unser Transport-Vehikel in die Cloud.

**3.1** Laden Sie die aktuelle `rclone.exe` (Windows amd64) von `rclone.org` herunter.

**3.2** Entpacken Sie die Datei auf dem `SRV-BKP-01` nach **`C:\rclone\`**.

**3.3** Öffnen Sie eine administrative PowerShell und wechseln Sie in das Verzeichnis: `cd C:\rclone`.

## Schritt 4: Google Drive anbinden

Wir authentifizieren rclone nun mit Ihrem Google-Konto.

**Rclone Setup starten**

```bash
.\rclone.exe config
```

Folgen Sie dem interaktiven Assistenten im Terminal:

- Drücken Sie **`n`** (New remote) und nennen Sie es **`GDrive`**.
- Geben Sie die Nummer für **Google Drive** ein (in neueren Versionen oft `18` oder ähnlich, suchen Sie in der Liste nach `drive`).
- *Client ID* und *Client Secret* können Sie leer lassen (Enter drücken).
- *Scope:* Wählen Sie **`1`** (Full access).
- *Service Account / Advanced Config:* Drücken Sie `Enter` (Nein).
- *Use auto config?* Drücken Sie **`Y`** (Ja). Es öffnet sich nun ein Webbrowser. Loggen Sie sich mit Ihrem Google-Konto ein und gewähren Sie rclone den Zugriff.
- Beenden Sie das Setup mit **`q`** (Quit).

## Schritt 5: Automatisierter Offsite-Sync

Damit Ihre Backups ohne manuelles Zutun in die Cloud wandern, erstellen wir ein simples PowerShell-Skript. Dieses synchronisiert die Veeam-Backups (z. B. von Laufwerk B: oder A:) verschlüsselt auf Ihr Google Drive.

**5.1** Erstellen Sie die Datei `C:\Scripts\CloudSync.ps1`:

**PowerShell: Offsite-Sync Skript**

```powershell
$RcloneExe = "C:\rclone\rclone.exe"
# Welche Backups sollen in die Cloud? (Pfade anpassen)
$SourcePath = "B:\VeeamBackups\"
$RemotePath = "GDrive:Veeam_Offsite_Backup"
# Startet den Sync. Löscht Dateien in der Cloud, wenn sie lokal (Retention) geloescht wurden.
& $RcloneExe sync $SourcePath $RemotePath --transfers 4 --checkers 8 --verbose --log-file "C:\Logs\rclone_sync.log"
```

*Als Datei:* [`scripts/10-backup-disaster-recovery/10.4-powershell-offsite-sync-skript.ps1`](../../scripts/10-backup-disaster-recovery/10.4-powershell-offsite-sync-skript.ps1)

**5.1 Veeam Integration (Post-Job Script):**

- Gehen Sie in Veeam in die Eigenschaften Ihres `JOB-Core-Infrastructure`.
- Unter **Storage** → **Advanced** → **Scripts** aktivieren Sie *„Run the following script after the job completes“*.
- Tragen Sie den Pfad zu Ihrem `CloudSync.ps1` ein.

> [!NOTE]
> **Portfolio-Check: 3-2-1 Compliance erreicht!**\
> Dokumentieren Sie diesen Meilenstein als finalen Beweis Ihrer Disaster-Recovery-Strategie:
>
> - **3 Kopien:** Produktivdaten (Hyper-V SSD), Lokales Backup (ReFS auf NAS), Offsite Backup (Google Drive).
> - **2 Medien:** SSD (Host) und HDD (NAS).
> - **1 Offsite:** Die Cloud. Sollte ein Cryptolocker das Netzwerk, die Hosts und das NAS verschlüsseln, bleibt das isolierte Cloud-Backup via rclone-API unangetastet.
