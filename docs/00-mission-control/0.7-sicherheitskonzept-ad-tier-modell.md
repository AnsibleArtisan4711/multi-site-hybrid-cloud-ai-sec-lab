# 0.7 Sicherheitskonzept (AD Tier-Modell)

## Das administrative Schichtenmodell (Tier-Modell)

Um das Active Directory vor Credential-Theft-Angriffen (wie Pass-the-Hash oder Pass-the-Ticket) zu schützen, wird von Beginn an ein striktes **Tier-Modell** (Schichtenmodell) nach Microsoft Best Practices implementiert. Dabei werden administrative Konten und Systeme in Vertrauensstufen (Tiers) isoliert.

| **Tier** | **Ebene** | **Ressourcen & Berechtigungen im Projekt** |
| --- | --- | --- |
| **Tier 0** | **Identity / Core** | **Systeme:** Domain Controller (SRV-DC-01, SRV-DC-02), OPNsense Firewalls, Entra Connect Server. **Regel:** Domain-Admins loggen sich AUSSCHLIESSLICH hier ein. |
| **Tier 1** | **Server / Dienste** | **Systeme:** Member-Server, NAS-Storage (STO-NAS-01), Webserver (SRV-WEB-01 in DMZ). **Regel:** Server-Admins verwalten diese Systeme, haben aber keine Rechte auf Tier 0. |
| **Tier 2** | **Workstations** | **Systeme:** Clients (CL-WIN-01, CL-UBU-01, CL-KALI-01). **Regel:** Helpdesk/Lokale Admins verwalten Endgeräte. Tier 0 und Tier 1 Konten dürfen sich hier niemals anmelden. |

## Maßnahmen zur technischen Durchsetzung

Ein Konzept auf dem Papier reicht nicht aus. Die Durchsetzung in der `ad.example.com` Domäne erfolgt durch folgende technische Barrieren:

- **Gruppenrichtlinien (GPOs):** Es werden GPOs erstellt, die dem Konto „Domänen-Admin“ das Recht *„Lokal anmelden“* sowie *„Anmelden über Remotedesktopdienste zulassen“* auf allen Computern der OUs „Workstations“ (Tier 2) und „Server“ (Tier 1) explizit verweigern.
- **Administrative Kontentrennung:** Der Administrator erhält mindestens zwei Konten (z. B. `adm-mvarga` für Tier 0 und ein Standardkonto `mvarga` für das tägliche Arbeiten am Tier 2 Client).
- **LAPS (Local Administrator Password Solution):** Wie in Modul 5.5 vorgesehen, wird LAPS implementiert. Dadurch erhält jeder Client und Member-Server ein individuelles, rotierendes lokales Administrator-Passwort. Ein Angreifer, der ein lokales Admin-Passwort auf `CL-WIN-01` ausliest, kann dieses nicht für einen lateralen Angriff auf andere Systeme verwenden.

## Namenskonvention für administrative Konten

Um die Zugehörigkeit eines Kontos zu einem bestimmten Tier sofort ersichtlich zu machen und versehentliche Logins mit falschen Rechten zu vermeiden, wird folgende Namenskonvention etabliert:

| **Konto-Typ / Tier** | **Präfix-Format** | **Beispiel & Verwendungszweck** |
| --- | --- | --- |
| **Standard-Benutzer** | `<nachname>` | `mvarga` Tägliches Arbeiten (E-Mail, Web, Office) auf Tier 2. Keine administrativen Rechte. |
| **Tier 2 Admin** | `adm-t2-<nachname>` | `adm-t2-mvarga` Lokaler Support auf Clients. Darf sich auf Workstations administrativ anmelden. |
| **Tier 1 Admin** | `adm-t1-<nachname>` | `adm-t1-mvarga` Server-Administration (Fileserver, Webserver). Darf sich NICHT auf Tier 0 oder Tier 2 anmelden. |
| **Tier 0 Admin** | `adm-t0-<nachname>` | `adm-t0-mvarga` Domain-Admin. Höchste Privilegien. Login ausschließlich auf Domain Controllern (Tier 0) gestattet. |
| **Service Accounts** | `svc-<dienst>-t<x>` | `svc-apache-t1` Dienstkonten für Applikationen, strikt an ihr jeweiliges Tier gebunden. |

**Sicherheitsphilosophie:**\
Wenn ein Client-PC (Tier 2) kompromittiert wird (z. B. durch Malware), darf der Angreifer im RAM des Clients niemals einen Token oder Hash eines Domain-Admins (Tier 0) finden. Die strikte Trennung der Anmeldung verhindert die Eskalation lokaler Rechte zur Domänenherrschaft.
