# 0.4 Domain-Strategie

## Festlegung des Active Directory Domain Namens

Für das Projekt wurde als interne Active Directory-Domäne **`ad.example.com`** festgelegt. Die externe Domain, welche primär für Cloud-Dienste (Microsoft 365, Entra ID) und das öffentliche Webhosting genutzt wird, lautet **`example.com`**.

## Architektonische Begründung (Das „Warum“)

Die Wahl einer dedizierten Subdomain (`ad.*`) für das interne Active Directory entspricht den Best Practices von Microsoft und löst ein entscheidendes Netzwerkproblem:

**Vermeidung von Split-Brain DNS und Auflösungskonflikten**\
Wäre der interne AD-Namespace exakt identisch mit der öffentlichen Domain (`example.com`), würden die internen Domain Controller alle DNS-Anfragen für diese Zone als autoritativ betrachten. Anfragen von internen Clients an die öffentliche Website (z. B. gehostet bei IONOS) würden an die IPs der internen Domain Controller geleitet und fehlschlagen (Auflösungskonflikt). Die Website wäre ohne manuell gepflegte A-Records im internen DNS von innen nicht erreichbar.

## Vorteile dieser Strategie für den Projektverlauf

- **Klare Zonen-Trennung:** Interne Namensauflösung (`ad.example.com`) und externe Namensauflösung überschneiden sich an keiner Stelle.
- **Sicherheit:** Interne Strukturdaten (SRV-Records, Hostnames der DCs) werden nicht in die öffentliche DNS-Zone im Internet geleakt.
- **Reibungsloser Hybrid-Betrieb (Modul 6):** Um Benutzern dennoch einen professionellen Login zu ermöglichen (z. B. `vorname@example.com` anstelle von `vorname@ad.example.com`), wird `example.com` zu einem späteren Zeitpunkt als alternativer UPN-Suffix (User Principal Name) im Active Directory „Domänen und Vertrauensstellungen“ konfiguriert. Dies schlägt die Brücke zu Microsoft 365.
