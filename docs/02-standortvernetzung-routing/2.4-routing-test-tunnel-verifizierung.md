# 2.4 Routing-Test & Tunnel-Verifizierung

## Zweck des Tests

Nach der erfolgreichen Konfiguration des WireGuard Site-to-Site VPNs (Modul 2.3) muss verifiziert werden, dass die OPNsense-Firewalls den Traffic aus dem lokalen HQ-Netz (`10.0.10.0/24`) korrekt durch den Tunnel in das Filial-Netz (`10.0.30.0/24`) routen und umgekehrt.

Hierfür verwenden wir die ICMP-Protokolle **Ping** (Erreichbarkeit) und **Traceroute** (Wegverfolgung).

## Schritt 1: Vorbereitung der Testumgebung

Um einen realistischen End-to-End-Test durchzuführen, müssen auf beiden Hyper-V Hosts entsprechende Client-VMs gestartet werden.

**1.1** Starten Sie auf **Host 1 (HQ)** die Linux-VM `CL-UBU-01`.

**1.2** Prüfen Sie über das Terminal (`ip a`), ob die VM eine IP im HQ-LAN hat (z. B. `10.0.10.15`).

**1.3** Starten Sie auf **Host 2 (Filiale)** die Linux-VM `CL-KALI-01`.

**1.4** Prüfen Sie auch hier die IP (z. B. `10.0.30.20`).

> [!IMPORTANT]
> **Praxis-Falle: Warum nehmen wir für den Test Linux und nicht Windows?**\
> Die Windows Defender Firewall blockiert in der Standardeinstellung (Öffentliches Netz) alle eingehenden ICMP Echo-Requests (Ping). Wenn Sie von der Filiale aus versuchen, `CL-WIN-01` im HQ anzupingen, wird dies fehlschlagen, selbst wenn der Tunnel perfekt funktioniert! Linux-Distributionen wie Ubuntu oder Kali antworten standardmäßig auf Pings, was den Netzwerktest wesentlich eindeutiger macht.

## Schritt 2: End-to-End Ping-Test

Öffnen Sie das Terminal auf dem HQ-Client (`CL-UBU-01`) und setzen Sie einen Ping auf die IP-Adresse des Filial-Clients ab.

**Ping vom HQ in die Filiale**

```text
root@CL-UBU-01:~# ping -c 4 10.0.30.20

PING 10.0.30.20 (10.0.30.20) 56(84) bytes of data.
64 bytes from 10.0.30.20: icmp_seq=1 ttl=62 time=3.12 ms
64 bytes from 10.0.30.20: icmp_seq=2 ttl=62 time=2.85 ms
64 bytes from 10.0.30.20: icmp_seq=3 ttl=62 time=2.91 ms
64 bytes from 10.0.30.20: icmp_seq=4 ttl=62 time=2.78 ms

--- 10.0.30.20 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3005ms
```

*Ergebnis:* Wenn Sie Antworten („64 bytes from...“) mit einer niedrigen Latenz (time) erhalten, steht der VPN-Tunnel und die Firewall-Regeln greifen korrekt.

## Schritt 3: Traceroute (Routenverfolgung)

Um zu beweisen, dass die Pakete wirklich durch den WireGuard-Tunnel fließen und nicht etwa über das physische 192er-Netzwerk ausweichen, führen wir ein *Traceroute* aus.

**Traceroute Analyse**

```text
root@CL-UBU-01:~# traceroute 10.0.30.20

traceroute to 10.0.30.20 (10.0.30.20), 30 hops max, 60 byte packets
 1  10.0.10.1 (10.0.10.1)  0.412 ms   # Gateway: OPNsense HQ
 2  10.254.254.2 (10.254.254.2)  1.825 ms   # VPN-Tunnel: OPNsense Filiale
 3  10.0.30.20 (10.0.30.20)  2.951 ms   # Ziel: Kali Linux
```

**Interpretation für das Portfolio:** Dieser Trace beweist die korrekte Architektur. Das Paket verlässt den Client zum Standard-Gateway (Hop 1). Das HQ-Gateway erkennt anhand der Routing-Tabelle, dass das 30er-Netz über das WireGuard-Interface (Hop 2) erreichbar ist. Danach stellt die Filial-Firewall das Paket im dortigen LAN zu (Hop 3).

## Schritt 4: Troubleshooting (Falls der Ping fehlschlägt)

Sollte die Verbindung nicht zustande kommen (z. B. *Request timed out*), prüfen Sie diese drei Kernpunkte:

1. **WireGuard Handshake (OPNsense):** Gehen Sie in OPNsense auf *VPN* → *WireGuard* → *List Configuration*. Sehen Sie dort unter dem Peer einen aktuellen Zeitstempel bei ***latest handshake***? Wenn nein, blockiert Ihr Heimrouter UDP-Port 51820 oder die Public/Private-Keys stimmen nicht überein.
2. **WireGuard Firewall-Regeln (Modul 2.3):** Haben Sie auf *beiden* Firewalls unter *Firewall* → *Rules* → *WireGuard* die „Pass Any to Any“-Regel (Action: Pass, Source: Any, Destination: Any) erstellt?
3. **Routing-Tabelle:** Haben Sie in der WireGuard Endpoint-Konfiguration unter *Allowed IPs* das jeweils andere Netz (`10.0.30.0/24` bzw. `10.0.10.0/24`) korrekt eingetragen?
