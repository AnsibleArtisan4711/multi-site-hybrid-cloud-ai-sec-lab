# 5.6 Linux AD-Logins (Test & Verifizierung)

## Zweck der Verifizierung

Nachdem der Edubuntu-Client (`CL-UBU-01`) in Modul 5.2 erfolgreich an das Active Directory (`ad.example.com`) angebunden wurde, muss die User Experience (UX) aus Sicht des Endbenutzers und des Administrators getestet werden. Wir verifizieren den lokalen grafischen Login, die Rechtezuweisung und die Kerberos-Ticket-Generierung.

Wir testen die Anmeldung mit dem in Phase 3 erstellten Standard-Benutzerkonto.

### Login-Prozess

**1.** Starten Sie die VM `CL-UBU-01` in Hyper-V.

**2.** Auf dem Anmeldebildschirm sehen Sie standardmäßig den lokalen Benutzer (z. B. `edubuntu`). Klicken Sie auf **Nicht aufgeführt?** (bzw. *Not listed?*).

**3. Benutzername:** Geben Sie den vollständigen User Principal Name (UPN) ein:

`mvarga@ad.example.com`.

**4. Passwort:** Geben Sie das zugehörige Windows-Passwort ein.

**5. Erster Start:** Der Desktop lädt. Im Hintergrund greift nun das in Modul 5.2 aktivierte PAM-Modul (`mkhomedir`) und erstellt vollautomatisch den persönlichen Ordner für diesen AD-Benutzer unter:\
`/home/mvarga@ad.example.com/`

Um zu beweisen, dass Linux die Benutzerdaten live vom Windows Domain Controller (`SRV-DC-01`) abruft, nutzen wir das Terminal. Öffnen Sie die Kommandozeile (Strg+Alt+T).

### Identitäts- und Gruppenabfrage

Führen Sie den Befehl `id` aus. Die Ausgabe sollte ähnlich wie folgt aussehen:

**Beweis der AD-Gruppenzugehörigkeit**

```bash
mvarga@CL-UBU-01:~$ id
uid=183401103(mvarga@ad.example.com)
gid=183400513(domain users@ad.example.com)
groups=183400513(domain users@ad.example.com),
183401104(grp_mitarbeiter@ad.example.com)
```

**Analyse:** Linux hat dem Benutzer eine eindeutige `UID` zugewiesen, die aus der Windows-SID (Security Identifier) berechnet wurde. Zudem erkennt Linux sofort, dass der Benutzer Mitglied in *Domain Users* und weiteren AD-Gruppen (z. B. *GRP\_Mitarbeiter*) ist.

**Rechte-Management (Tier-Modell Test)**

In Modul 5.2 haben wir festgelegt, dass der **Tier-2 Administrator** Root-Rechte (`sudo`) auf diesem Linux-Client erhält. Der Standard-Benutzer darf diese Rechte nicht haben.

### Test A: Standard-Benutzer

Versuchen Sie als `mvarga@ad.example.com` das System zu aktualisieren:

```bash
sudo apt update
```

*Erwartetes Ergebnis:* Sie werden nach dem Passwort gefragt und erhalten danach die Fehlermeldung: *„mvarga is not in the sudoers file. This incident will be reported.“* Das Tier-Modell greift perfekt!

### Test B: Tier-2 Admin

**1.** Melden Sie sich vom GUI ab und als `adm-t2-mvarga@ad.example.com` an.

**2.** Öffnen Sie das Terminal und führen Sie `sudo apt update` aus.

**3.** *Erwartetes Ergebnis:* Der Befehl wird erfolgreich und mit Root-Rechten ausgeführt.

**Portfolio-Highlight: Kerberos-Tickets (SSO)**

Der größte Vorteil einer AD-Integration ist Kerberos. Wenn sich der Benutzer am Linux-System anmeldet, erhält er vom Domain Controller im Hintergrund ein *Ticket Granting Ticket (TGT)*.

### Kerberos-Ticket auslesen

Führen Sie im Terminal den Befehl `klist` aus:

**Auslesen des Kerberos-Tickets**

```bash
mvarga@CL-UBU-01:~$ klist
Ticket cache: FILE:/tmp/krb5cc_183401103_aB3dE
Default principal: mvarga@AD.EXAMPLE.COM

Valid starting       Expires              Service principal
12/04/2023 09:00:00  12/04/2023 19:00:00  krbtgt/AD.EXAMPLE.COM
```

> [!NOTE]
> **Was bedeutet das für Ihr Projekt?**\
> Da dieses `krbtgt`-Ticket im Linux-Speicher liegt, verfügt der Client nun über **Single Sign-On (SSO)**. Wenn der Benutzer nun über den Dateimanager auf das NAS zugreifen möchte (`smb://10.0.10.250/Projekte`), wird er nicht erneut nach einem Passwort gefragt. Linux reicht das Kerberos-Ticket automatisch an das NAS (SMB-Share) weiter und gewährt naht-
>
> losen Zugriff.
