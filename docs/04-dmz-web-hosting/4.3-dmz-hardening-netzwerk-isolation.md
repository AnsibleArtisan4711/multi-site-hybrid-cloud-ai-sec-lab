# 4.3 DMZ Hardening & Netzwerk-Isolation

## Das Sicherheits-Paradigma: Zero Trust DMZ

Ein Webserver ist aufgrund seiner Natur (Erreichbarkeit aus dem Internet) das am stärksten gefährdete System in Ihrer Infrastruktur. Das Ziel des Hardening-Moduls ist es, den Schaden bei einer erfolgreichen Kompromittierung des `SRV-WEB-01` zu begrenzen (*Blast Radius Reduction*). Die Firewall-Regeln werden so konfiguriert, dass der Webserver eine reine „Einbahnstraße“ ist: Er empfängt Daten, darf aber keine neuen Verbindungen in interne Netze initiieren.

## Schritt 1: Definition der Aliasse (Best Practice)

Um die Firewall-Regeln übersichtlich zu halten, erstellen wir in OPNsense unter **Firewall** → **Aliases** Gruppen für unsere internen Netze.

- **Alias Name:** `INTERNAL_NETWORKS`
- **Inhalt:** `10.0.10.0/24` (HQ LAN), `10.0.30.0/24` (Filiale LAN).

## Schritt 2: Implementierung der Regel-Hierarchie

Navigieren Sie in der OPNsense WebGUI zu **Firewall** → **Rules** → **DMZ**. Die Regeln werden von **oben nach unten** abgearbeitet.

| **Aktion** | **Protokoll** | **Quelle** | **Ziel** | **Bedeutung** |
| --- | --- | --- | --- | --- |
| **Pass** | DNS (UDP) | DMZ net | DMZ address | Erlaubt dem Server, die Firewall nach IP-Adressen zu fragen. |
| **Block** | Any | DMZ net | INTERNAL\_NETWORKS | **Kern-Isolation:** Der Webserver darf niemals eine Verbindung zum DC oder den Clients aufbauen. |
| **Pass** | Any | DMZ net | any | Erlaubt dem Server den Zugriff auf das Internet (z. B. für `apt upgrade`). |

## Schritt 3: Host-Hardening auf Ubuntu

Zusätzlich zur Netzwerk-Firewall minimieren wir die Angriffsfläche auf dem Ubuntu-Server selbst.

**Sicherheits-Konfiguration auf SRV-WEB-01**

```bash
# 1. Unnötige Dienste identifizieren und beenden
sudo ss -tulpn

# 2. Automatische Sicherheits-Updates aktivieren
sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades

# 3. SSH-Login einschränken (Passwort-Login deaktivieren, nur Keys erlauben)
# Editieren Sie /etc/ssh/sshd_config:
# PasswordAuthentication no
# PubkeyAuthentication yes
sudo systemctl restart ssh
```

## Schritt 4: Verifizierung der Blockierung (Der „Beweis“)

Ein essenzieller Teil Ihres Portfolios ist der Nachweis, dass die Sperre funktioniert. Führen Sie vom Webserver (`10.0.20.80`) folgende Tests aus:

**Test 1: Ping zum Internet:** `ping -c 3 8.8.8.8` → **Erfolgreich**.

**Test 2: Ping zum Domain Controller:** `ping -c 3 10.0.10.10` → **Fehlgeschlagen** (Timeout).

**Test 3: SSH-Versuch zum DC:** `ssh 10.0.10.10` → **Fehlgeschlagen**.

> [!WARNING]
> **Kritischer Hinweis zur Replikation:**\
> Beachten Sie, dass die Regel „Block DMZ to INTERNAL\_NETWORKS“ auch den Zugriff auf den `SRV-DC-02` in der Filiale unterbindet. Dies ist absolut gewollt. Ein Webserver hat keinen legitimen Grund, mit einem Domain Controller zu kommunizieren, es sei denn, Sie nutzen LDAP-Authentifizierung für eine Website – in diesem Fall müsste eine spezifische *Pass*-Regel für Port 636 (LDAPS) **über** die Block-Regel geschoben werden.
