# 12.6 Übergabe-Protokoll (Cleanup & Dauer-Admins)

## Zweck des Übergabe-Protokolls

Bevor eine aufgebaute IT-Infrastruktur vom Projekt-Team an den regulären IT-Betrieb (Operations) oder einen externen Prüfer übergeben wird, muss sie bereinigt werden. Während der Aufbau- und Testphase (Phasen 1 bis 11) entstehen oft temporäre Testkonten, vereinfachte Passwörter oder Ausnahmeregeln.

Dieses Dokument beschreibt den finalen „Cleanup-Prozess“ sowie die Einrichtung hochsicherer Notfall-Zugänge (*Break-Glass Accounts*), die zusammen mit der Dokumentation an das Management übergeben werden.

## Schritt 1: Bereinigung (Cleanup) der Infrastruktur

Alle Altlasten aus der Projektphase müssen vor dem Go-Live entfernt werden.

**1.1 Temporäre Konten löschen / deaktivieren:**

- Löschen Sie im Active Directory (`SRV-DC-01`) Testbenutzer, die nur für Modul-Tests verwendet wurden.
- Falls der Account `schulung@example.com` nicht mehr benötigt wird, entziehen Sie ihm im M365 Admin Center die Lizenz (um Kosten zu sparen) und löschen Sie das Objekt lokal.

**1.2 Temporäre Firewall-Regeln entfernen:**

- Entfernen Sie in der OPNsense die „Allow Any“-Testregeln (falls abweichend von Modul 2.6 erstellt).
- Deaktivieren Sie das Ping-Echo (ICMP) auf WAN-Schnittstellen, falls dies für temporäre Tests aktiviert wurde.

**1.3 Initial-Passwörter rotieren:**

- Ändern Sie das `root`-Passwort der beiden OPNsense-Firewalls und des Ubuntu-Webservers.
- Ändern Sie das `admin`-Passwort des UGreen NAS und der lokalen Hyper-V Hosts.

**1.4 LAPS-Rotation erzwingen:**

- Öffnen Sie die PowerShell auf dem DC und erzwingen Sie eine sofortige Neugenerierung aller lokalen LAPS-Passwörter auf den Clients, um sicherzustellen, dass keine alten Passwörter aus der Testphase mehr gültig sind: `Reset-LapsPassword -Identity *`

## Schritt 2: Anlage von Notfall-Administratoren (Break-Glass)

Wenn alle regulären Administratoren ausgesperrt sind (z. B. durch einen Fehler in Entra ID MFA oder korrupte Smartcards), muss ein dokumentierter Notnagel existieren.

### 2.1 Cloud Break-Glass Account (M365 / Entra ID)

Erstellen Sie einen Administrator, der nicht von lokalen Systemen abhängig ist.

- **Typ:** *Cloud-Only* Account (wird nicht vom lokalen AD synchronisiert).
- **Username:** z. B. `breakglass-admin@contoso.onmicrosoft.com` (Nutzen Sie die Fallback-Domain, nicht die benutzerdefinierte Domain).
- **Rolle:** Globaler Administrator.
- **Sicherheit:** Ein extrem langes (30+ Zeichen), zufällig generiertes Passwort. **Achtung:** Dieser Account MUSS von Conditional Access MFA-Richtlinien (oder Security Defaults) ausgenommen sein!

### 2.2 Lokaler Directory Services Restore Mode (DSRM)

Das in Modul 3.1 vergebene **DSRM-Kennwort** ist der einzige Weg, um sich lokal an einem Domain Controller anzumelden, wenn das Active Directory (die NTDS.dit-Datenbank) defekt ist.

- Prüfen Sie, ob dieses Passwort korrekt im Passwort-Safe dokumentiert wurde.

## Schritt 3: Das Übergabe-Paket (Handover Package)

Folgende Dokumente und Datensätze werden physisch oder verschlüsselt an den neuen Betriebsverantwortlichen (Operations) übergeben:

| **Bestandteil** | **Inhalt & Zweck** |
| --- | --- |
| **1. Passwort-Tresor** | Exportierte KeePass-Datei (`.kdbx`) oder Bitwarden-Vault mit allen finalen Tier-0, Tier-1 und Service-Account Passwörtern sowie dem **DSRM-Kennwort** und dem **Google Drive (Veeam) AES-256 Key**. |
| **2. Visio-Diagramme** | Die logischen und physischen Netzpläne (Modul 12.1). |
| **3. Systemhandbuch** | Dokumentation von AD, GPOs und Backup-Routinen (Modul 12.2). |
| **4. Runbook (DR)** | Der Schritt-für-Schritt Notfallplan bei Ransomware/Ausfall (Modul 12.4). |
| **5. Lizenz-TCO** | Übersicht der Laufzeiten und M365-Kosten (Modul 12.5). |
| **6. AI-Sec Report** | Die Analyseergebnisse und Performance-Werte des Ollama SIEM-Hubs zur Vorlage bei der IT-Sicherheit (Modul 12.3). |
